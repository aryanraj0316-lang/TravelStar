## 0.2 The consistency contract

The word "consistent" is the single most important requirement in this brief. Before Phase 1, create `docs/CONVENTIONS.md` containing the following contracts, and then **enforce them everywhere, without exception**.

### 0.2.1 API response envelope

Every endpoint returns exactly one of these shapes. No exceptions, no variations.

```ts
// Success
{ "ok": true, "data": T, "meta"?: { "cursor"?: string, "total"?: number } }

// Failure
{ "ok": false, "error": { "code": "TRIP_NOT_FOUND", "message": "Human readable", "details"?: unknown } }
```

- `error.code` is a `SCREAMING_SNAKE_CASE` member of a single exported union type shared by client and server.
- HTTP status is always meaningful: 400 validation, 401 unauthenticated, 403 unauthorised, 404 not found, 409 conflict, 422 business-rule violation, 429 rate limited, 500 unexpected.
- The client's `request()` unwraps `data` on `ok: true` and throws a typed `ApiError` on `ok: false`. It never returns `null` to signal failure.

### 0.2.2 Money

- Stored in Postgres as `Decimal @db.Decimal(12, 2)`. Never `Float`.
- Transported over the wire as a **string** (`"8500.00"`) to avoid JS float loss.
- Represented in the client by a single `Money` type and formatted only through one helper: `formatINR(value: Money): string` → `"₹8,500"`.
- Never format currency inline with template strings again. Delete every `₹${x.toLocaleString('en-IN')}` in the codebase and route it through the helper.

### 0.2.3 Dates and times

- Stored as `timestamptz`. Transported as ISO 8601 UTC strings.
- All display formatting goes through `formatDate`, `formatTime`, `formatRelative` in `src/lib/datetime.ts`. Timezone is `Asia/Kolkata` unless the user's device says otherwise.
- Delete every ad-hoc `new Date(x).toLocaleTimeString([], {...})` and `"14 mins ago"` string literal.

### 0.2.4 IDs

- All entity IDs are UUIDs generated by the database. The client never invents an ID (`\`trip-${Date.now()}\`` is banned).
- Idempotency keys, where needed, are client-generated UUIDv4 and sent in an `Idempotency-Key` header.

### 0.2.5 Screen state machine

Every screen that loads remote data implements exactly four states, using one shared component set:

`<ScreenLoading />` · `<ScreenError onRetry />` · `<ScreenEmpty title action />` · content

No screen may render content while data is still `undefined`. No screen may show a spinner forever.

### 0.2.6 User feedback

- `Alert.alert` is banned (it no-ops on web, and this app ships web). Replace with a single cross-platform `<Dialog>` / `useConfirm()` and a `toast()` API in `src/lib/feedback.ts`.
- Success toast for every successful mutation. Error toast with the `error.message` for every failure. No exceptions.

### 0.2.7 Design tokens

- **One** palette, in `src/constants/theme.ts`. Every local `const C = { bg: '#060814', ... }` object in every screen is deleted and replaced with tokens from the theme.
- Currently `#060814`, `#070913`, `#0A0C16`, and `#080A12` are all used as "the background". Pick one. Same for every other near-duplicate.
- Spacing comes only from the `Spacing` scale. Radii from a `Radii` scale you will add. Typography from a `Typography` scale you will add — no more inline `fontSize: 8.5`.

### 0.2.8 Naming

- Backend routes: `kebab-case` paths, plural resources: `/api/v1/trips/:tripId/join-requests`.
- TS files: `kebab-case.ts(x)`. React components: `PascalCase`. Hooks: `useThing`.
- One vocabulary for the domain. Right now the code calls the same thing a *trip*, a *tour*, a *route*, a *group*, and an *expedition*. Choose **Trip** and rename everything else.
- The product has one name. Right now it is simultaneously "Tourism", "TravelStar", "TravelConnect India", and "travelconnect-backend". Choose one (I'll assume **TravelStar**) and apply it to `app.json` name/slug/scheme, the Android package, both `package.json` names, the LICENSE, and all UI copy.

# PHASE 2 — Security and authentication

**This phase is non-negotiable and nothing may ship before it is complete.** The application currently has a complete authentication bypass, plaintext passwords, and broadcasts users' live GPS coordinates to every connected client.

## 2.1 Fix the account-takeover bug in registration

`backend/src/api/routes/auth.ts`, `POST /register`:

```ts
let user = await prisma.user.findFirst({ where: { email: userEmail }, ... });
if (!user) { user = await prisma.user.create({ ... }); }
// falls straight through and issues a token
const token = jwt.sign({ id: user.id, ... }, JWT_SECRET, { expiresIn: '7d' });
```

If the email already exists, registration does not fail — it skips creation and issues a valid 7-day session **without checking the password**. `POST /auth/register {"email":"tourist@travelstar.com"}` returns a working session for that account.

Fix: return `409 EMAIL_ALREADY_REGISTERED`. Never issue a token from a registration path for an existing account.

## 2.2 Hash passwords

`passwordHash` currently stores the raw password, and login does `user.passwordHash !== password`. There is also a `'default_password'` literal fallback that creates accounts with a known credential, and the seed commits `password123`.

- Use `argon2id` (preferred) or bcrypt with cost ≥ 12.
- Constant-time comparison via the library's `verify`.
- Enforce a password policy: minimum 10 characters, checked against a common-password list (`zxcvbn` or a top-10k list).
- Remove the `'default_password'` fallback — a registration without a password is a `400`.
- Add a forced-reset migration path for any existing rows.
- Implement a real password-reset flow (email token, single use, 30-minute expiry, invalidates sessions).

## 2.3 Delete the shared `activeProfile` singleton

`auth.ts` holds `let activeProfile` at module scope. `GET /auth/profile` returns it when there is no valid token — meaning **any unauthenticated caller receives the profile of whoever most recently logged in**, including email, phone, wallet balance and emergency contact. `PUT /auth/profile` mutates it and can write to that user's DB row via `targetUserId = userId || activeProfile.id`.

Delete the variable and every reference to it. There is no legitimate "current user" at module scope in an HTTP server. Identity comes from the verified token, always.

## 2.4 Actually apply the auth middleware

`backend/src/middleware/auth.ts` exports a correct `authenticateJWT` and `requireRole`. **Neither is imported anywhere.** Instead seven route files copy-paste a local `getUserIdFromReq` that returns `null` on failure, and callers then fall back to an arbitrary user.

**Do this:**
1. Mount `authenticateJWT` globally: `app.use('/api/v1', authenticateJWT)`, with an explicit public allowlist for `POST /auth/login`, `POST /auth/register`, `POST /auth/forgot-password`, `POST /auth/reset-password`, and `GET /health`.
2. Delete all seven copies of `getUserIdFromReq` from `auth.ts`, `chats.ts`, `guides.ts`, `interactions.ts`, `notifications.ts`, `safety.ts`, `trips.ts`.
3. Type `req.user` via module augmentation so `req.user.id` is non-optional inside authenticated handlers.
4. **Delete every `prisma.user.findFirst()` fallback.** These appear in `interactions.ts` (join-request, join-requests, cancel), `safety.ts` (SOS), `trips.ts` (create), and `server.ts` (sendMessage, triggerSOS). Each one turns an unauthenticated request into "the first user in the database". No token → 401. Full stop.

## 2.5 Fix authorization — the IDOR endpoints

Every one of these mutating endpoints currently has **no ownership check**. Add one to each, returning `403 FORBIDDEN` on mismatch:

| Endpoint | Required check |
|---|---|
| `POST /interactions/join-request` | `userId` must come from the token, never the request body |
| `POST /interactions/like` | same; remove the `'default-user'` default from `TripLike.userId` |
| `POST /notifications/:id/read` | notification must belong to `req.user.id` |
| `POST /safety/sos/:id/resolve` | only the alert owner, an assigned responder, or an admin — **currently anyone can silently resolve a stranger's active distress signal** |
| `DELETE /safety/contacts/:id` | contact must belong to `req.user.id` |
| `POST/PUT/DELETE /guides/:id/packages` | the guide profile must belong to `req.user.id` |
| `POST /guides/:id/live-status` | same — currently anyone can spoof any guide's GPS |
| `POST /trips/:id/join` | authenticated, and subject to the seat transaction in Phase 3 |
| `GET /guides/:id/earnings` | only that guide or an admin |
| `GET /guides/:id/leads` | only that guide or an admin |

Then write an integration test per row that asserts a 403 for a non-owner. **Add this as a permanent CI gate: no route handler may reach the DB without an explicit authorization assertion.**

## 2.6 Stop minting fake verified guides

`GET /guides/profile` auto-creates a `GuideProfile` when one doesn't exist, with a fabricated `licenseNumber`, a stock-photo `licensePhotoUrl`, `experienceYears: 5`, and **`verifiedStatus: 'VERIFIED'`**. One GET request produces a verified tour-guide identity on a marketplace where "Verified Guide" is the trust signal users pay on.

- A `GET` must never create rows. Return `404 GUIDE_PROFILE_NOT_FOUND`.
- Add `POST /guides/profile` that creates a profile with `verificationStatus: PENDING` and requires a real licence number and document upload.
- Build an admin review queue. `VERIFIED` is set only by an admin action, recorded in `AdminLog` with the reviewing admin's ID.

## 2.7 Secrets management

`const JWT_SECRET = process.env.JWT_SECRET || 'super_secret_jwt_key_travelconnect_12345'` appears in **eight files**, and the identical value is committed in `.env.example`.

- Create `backend/src/config/env.ts` that parses `process.env` with zod at boot and **throws on startup** if `JWT_SECRET`, `DATABASE_URL`, or any other required var is missing or (for the secret) shorter than 32 bytes.
- No fallback values, ever.
- Import the typed config object everywhere; delete all eight literals.
- Rewrite `.env.example` with empty values and comments only.
- Rotate the secret and document rotation in a runbook.

## 2.8 Token lifecycle

- Short-lived access token (15 min) + rotating refresh token stored server-side (a `Session` table with `id`, `userId`, `tokenHash`, `expiresAt`, `revokedAt`, `userAgent`, `ip`).
- Refresh-token rotation with reuse detection: a replayed refresh token revokes the whole session family.
- `POST /auth/logout` revokes the session server-side. Currently logout is purely client-side, so a stolen token stays valid for 7 days.
- Client: store tokens in `expo-secure-store` (Keychain/Keystore), **not** AsyncStorage/`localStorage` as `safeStorage` does today.
- Client: a single 401 interceptor that attempts refresh once, and on failure clears the session and routes to `/auth` with a "session expired" toast. Currently a 401 returns `null` and every screen silently renders empty forever.

## 2.9 Fix `safeStorage`

It currently swallows all errors into an in-memory `Map`, so if the native module is unavailable the token "saves" to memory, dies with the process, and the user appears logged in while every request 401s.

Rewrite it to: try secure storage → on failure, **throw a typed `StorageUnavailableError`** → the auth flow surfaces "Unable to save your session on this device" rather than proceeding. Never fall back to memory for credentials.

## 2.10 Transport and network hardening

- **HTTPS only.** Everything is currently `http://`, which iOS ATS and Android cleartext policy both block anyway. Terminate TLS at the load balancer; enforce HSTS.
- Certificate pinning for the mobile app (consider `react-native-ssl-pinning`) — optional but recommended given the Aadhaar data.
- Replace `cors({ origin: '*' })` on both Express and Socket.io with an explicit allowlist from config.
- `helmet` is applied but unconfigured — set a real CSP for the web build, `referrerPolicy`, `noSniff`, `frameguard`.
- **Rate limiting:** currently a single `1000 req / 15 min / IP` across all of `/api/`, which is ~1.1 req/sec of unlimited password guessing. Add per-route limits: `POST /auth/login` 5/15min per IP **and** per email, `POST /auth/register` 3/hour per IP, `POST /safety/sos` 10/hour per user, write endpoints 60/min per user. Add progressive account lockout with a captcha or device-attestation escalation.
- Add request body size limits per route (the global `10mb` is far too generous for JSON endpoints).

## 2.11 Fix the client's unauthenticated profile write

`src/store/AppContext.tsx`:

```ts
useEffect(() => {
  setProfile(prev => ({ ...prev, role: currentRole }));
  apiService.updateProfile({ role: currentRole });   // fires on mount, logged out, no token
}, [currentRole]);
```

This fires an unauthenticated PUT on every cold start. Combined with §2.3 it mutated the server's shared profile. Guard every mutation on an authenticated session, and never let a role change be a client-side assertion — role changes go through a server-side authorization check.

## 2.12 Fix logout

```ts
const nextProfile = { ...prev, name: 'Guest Traveler', email: '', phoneNumber: '', ... };
safeStorage.setItem('savedProfile', JSON.stringify(nextProfile));
```

It keeps `id`, `avatar`, `bio`, `walletBalance`, `rewardPoints`, `emergencyContact`, `languages` on disk. Logout must: revoke the server session, delete every storage key, reset context to a fresh default object, disconnect the socket, and clear any query cache.

# PHASE 3 — Real-time layer

The Socket.io layer is currently the highest-liability code in the repository.

## 3.1 Authenticate the socket handshake

```ts
const userId = socket.handshake.query.userId as string;
if (userId) { socket.join(userId); }
```

`userId` is taken from the query string and trusted. Connect with `?userId=<any-uuid>` and you join that user's private notification room, receiving their `notificationReceived` and `addedToChat` events.

Fix: `io.use()` middleware that verifies the JWT from `socket.handshake.auth.token`, attaches `socket.data.userId`, and rejects the connection otherwise. Derive room membership from `socket.data.userId` only.

## 3.2 Authorize room joins

```ts
socket.on('joinRoom', async (roomId: string) => { socket.join(roomId); /* no check */ });
```

Any client can emit `joinRoom` with any chat room ID and the server replies with the **entire message history** of a trip they are not a member of.

Fix: check `ChatRoomMember` for `(roomId, socket.data.userId)` before joining. Emit an error and refuse otherwise.

## 3.3 Fix message attribution

```ts
const user = await prisma.user.findFirst({
  where: { profile: { firstName: data.senderName.split(' ')[0] } }
});
senderId = user?.id || (await prisma.user.findFirst())?.id;
```

The client never sends `senderId`, so the server guesses the author by **first-name string match**, and on a miss attributes the message to *the first user in the entire database*. This is unrecoverable corruption of a chat log.

Fix: `senderId = socket.data.userId`, always. Never accept a sender identity from the payload. Validate the payload with zod. Then audit existing message rows for misattribution and decide with me how to handle them.

## 3.4 Stop broadcasting SOS alerts and GPS to everyone

```ts
io.emit('sosReceived', alert);                                    // { userName, latitude, longitude }
socket.broadcast.emit('locationUpdated', { userId, latitude, longitude });
```

This streams every user's real-time GPS position, and the name and coordinates of anyone in distress, to **every device with the app open**. Under India's DPDP Act and GDPR, precise location is sensitive personal data. A publicly broadcast SOS beacon also puts the person in *more* danger.

Fix:
- SOS is emitted only to: the alerting user's registered emergency contacts who are app users, the members of their active trip, the assigned guide, and authenticated users holding an `ADMIN`/responder role.
- Location updates are emitted only to the trip room the user is currently in, and **only if `Profile.locationSharing` is true** — that toggle currently does nothing.
- Add a visible in-app indicator whenever location is being shared, and a one-tap stop.
- Log every SOS emission and every location-share session for audit.

## 3.5 Handle `roomHistory` on the client

The server emits `socket.emit('roomHistory', { roomId, messages: history })` on join. `src/services/socket.ts` registers listeners for `messageReceived`, `addedToChat`, `notificationReceived`, `sosReceived`, `sosResolved`, `locationUpdated`, and `walletUpdated` — **but not `roomHistory`**. History fetched over the socket is silently discarded.

Either wire up the listener, or (preferred) drop history-over-socket entirely and load it via the paginated REST endpoint, keeping the socket for live deltas only. Pick one and be consistent.

## 3.6 Restructure client message state

`AppContext.messages` is one flat array accumulating every message from every room, seeded with three mock messages that have **no `roomId` at all** — so they leak into whichever room is open. There is no eviction, so a long session grows unboundedly.

Fix: store messages keyed by room (`Record<roomId, Message[]>`), cap in-memory history per room, add cursor pagination, and remove the mock seeds.

## 3.7 Optimistic sending

A sent message currently only appears after a full server round-trip. Add optimistic insertion with a client-side temp ID, a `sending | sent | failed` status, reconciliation on the server ack, and a retry affordance on failure.

## 3.8 Make the socket layer horizontally scalable

`server.ts` keeps `roomMessages` and `activeUserLocations` as module-level `Map`s. These are per-process, never evicted (a slow memory leak), lost on restart, and make running two instances impossible.

- Delete `roomMessages` entirely — Postgres is the source of truth.
- Move presence/location into Redis with a TTL.
- Add the Socket.io Redis adapter so rooms span instances.
- Add heartbeat/reconnect handling and a connection-state indicator in the chat UI.

## 5.1 Validation on every boundary

## 5.2 Async error handling

## 5.3 Eliminate all module-level mutable state

## 5.4 Fix the seat-booking race

```ts
const dbTrip = await prisma.trip.findUnique({ where: { id } });
if (dbTrip.availableSeats > 0) {
  await prisma.trip.update({ data: { availableSeats: dbTrip.availableSeats - 1 } });
}
```

Read-modify-write with no transaction: two concurrent joins both read `1`, both write `0`, and the trip is oversold. The approval path in `interactions.ts` uses `{ decrement: 1 }` but still gates on a stale `request.trip.availableSeats`.

Also: this endpoint creates **no `TripMember` row**, and rejecting a previously-approved request never restores the seat.

Fix: a single transaction containing a conditional update (`UPDATE trips SET "availableSeats" = "availableSeats" - 1 WHERE id = $1 AND "availableSeats" > 0` — check `rowCount`), the `TripMember` insert, the `JoinRequest` status change, the chat-room membership, and the notification. Add a `availableSeats >= 0` check constraint. Write a concurrency test that fires 50 simultaneous joins at a 10-seat trip and asserts exactly 10 succeed.

## 5.5 Rebuild payments properly — or remove them

Current state of `payments.ts`:

```ts

  const { bookingId, paymentId, signature } = req.body;
  if (!signature) return res.status(400)...;
  res.status(200).json({ paymentStatus: 'SUCCESS', gstInvoiceId: `GST-${Date.now()}`, ... });

```

There is no gateway integration, no HMAC verification, no webhook, no idempotency, and **nothing is written to `Booking` or `Payment`**. Any truthy string passes. The client then shows the user a "GST Invoice" ID for a transaction that never happened — that is not merely a bug, it is a tax-document problem.

**Decision required from me before you build.** Then either:

**(A) Implement properly:**
- Server-side order creation with a real gateway (Razorpay for India).
- Client opens the gateway checkout SDK — never a hand-rolled payment form (`DummyPaymentModal` must be deleted).
- Payment state transitions driven **only by verified webhooks** with HMAC signature validation, not by the client reporting success.
- Idempotency keys on order creation; webhook replay protection.
- A `Payment` state machine: `CREATED → PENDING → AUTHORIZED → CAPTURED → SETTLED`, plus `FAILED` and `REFUNDED`, with every transition persisted and audited.
- Refunds, partial refunds, and a cancellation policy.
- GST at the legally correct rate for the service category (the current flat 18% in `DummyPaymentModal` is wrong for several travel categories) — and real invoices from an accounting integration, not `\`GST-${Date.now()}\``.
- PCI scope stays zero: card data never touches your servers.

**(B) Remove entirely:** strip the payment UI, mark trips as "payment on arrival", and ship without it. This is a legitimate v1 choice and far better than shipping (A) badly.

## 5.6 Rebuild the wallet


## 6.1 Fix the API base URL — the app currently cannot reach any real backend

## 6.2 Rewrite `request()`

Every screen currently does `useEffect(() => { api.getX().then(setX) }, [])` with no cache, no dedup, no retry, no stale-while-revalidate, and no offline handling. On Indian mobile networks — the actual target market — this app will feel broken on every subway ride.

Adopt **TanStack Query**:
- One `queryKey` factory module so keys are consistent across the app.
- Mutations with `onMutate` optimistic updates, `onError` rollback, and `onSettled` invalidation.
- `persistQueryClient` with AsyncStorage for offline reads.
- A mutation queue for offline writes (join requests, messages, SOS) that flushes on reconnect.
- `NetInfo`-driven online/offline banner.

Delete the hand-rolled fetching in every screen as you migrate it.

## 6.4 Generate the client types from the server
